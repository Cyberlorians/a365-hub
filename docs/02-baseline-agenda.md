# A365 Hub: Delivery and Customer Value Playbook

## The pitch

**Adopt AI. Govern Agents. Protect the Business.**

AI agents can act with legitimate access and still put business information at risk.
This attack-informed workshop connects Entra, Agent 365, Purview, and Defender /
integrated security operations so customers can adopt useful AI with accountable
ownership, intentional access, supported data controls, and actionable evidence.

The workshop is the vehicle; secure AI adoption is the offer.

## The security spine

**Risk -> control -> evidence -> decision**, in every module, anchored in the
Cloud-Architekt Agent Identities chapter. The five Entra pillars provide the identity
control structure, but identity alone does not close the AI-native attack surface.

A correctly authenticated agent can be manipulated into misusing legitimate tools.
Injection need not cause a new IdP event at ingestion; subsequent authentication and
resource activity can still produce identity evidence. Add runtime/tool, data, and
applicable network evidence rather than treating identity logs as sufficient or irrelevant.

## Customer outcomes and commercial moments

| Moment | Demonstrable value | Honest next question |
|---|---|---|
| Useful approved task | A bounded business action, actual actor and evidence | What remains unproven? |
| Identity/authority map | Effective grants, accountability, and blast radius | Is access intentional and justified? |
| Governance decision | Reviewed sponsor/technical rights and lifecycle | Who owns renewal/remediation? |
| Data-control test | Actual supported audit/warn/block result | Which sensitive-data gap remains? |
| Investigation/response | Attributed evidence and scoped verified action | What coverage/operational work is required? |
| Pilot decision | Owned actions, success measures, and rollout boundary | Which entitlements and costs fit the measured gap? |

**Motion:** workshop -> readiness assessment -> scoped pilot -> licensing decision ->
broader adoption.

E7 brings connected capabilities together; compare existing subscriptions and eligible
alternatives. Do not make basic DLP, ordinary XDR, ISOC, or every shown function E7-exclusive.
Recheck feature licensing, preview availability, Azure usage, ingestion/retention, and
capacity costs before customer advice.

## Operating model

Use one customer case with explicit technical targets. The candidate toolkit Mail task
and GBB AI-workload fixture are initially separate. Join only by verified typed keys.
Use current `AgentsInfo` and supported activity/behavior/alert schemas after validation.
Current DLP tuning may produce behaviors instead of incidents; do not change global
tuning to manufacture an alert.

ISOC completes the connected security-operations story. Its current preview has
workspace/eligibility conditions; existing Sentinel customers keep their supported
experience. Entra/Purview management and Compliance Manager do not all move into ISOC.
Automation and generated playbooks require human review, permissions, testing, and
explicit activation.

## First-release sequence

1. Review the [Module 1](../slides/module-01/README.md) and
   [Module 2](../slides/module-02/README.md) content drafts.
2. Approve an isolated test-user, synthetic-data, runtime, automation, cost, and reset plan.
3. Prove actual authority, internal receipt, and evidence; then finalize the activity.
4. Test two fresh learners and failure/reset paths; rehearse independently.
5. Publish/label the appropriate hands-on release only when its gates pass.
