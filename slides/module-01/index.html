Part 2 / Why agents need security

See It.
Control It.
Protect It.

An AI agent is a digital coworker. It reads, makes decisions, and acts with real access.

See it

Know the agent's purpose, owner and operating context.

Control it

Approve its access, data and tool boundaries.

Protect it

Check what happened and act on the evidence.

Companies want agents for the work they do. Our job is to see them, control them and protect them.

What you are learning: know what to ask before you trust an agent.

Learn the basics / From an answer to an action

An agent can use tools to do a job.

Meet our example support agent. An employee asks: “My laptop will not start. Can you help and open a support ticket?”

  1. 1

    The request

    The employee gives the agent a job: help with the laptop and request support.

  2. 2

    The information

    The agent uses an approved troubleshooting guide to provide useful instructions.

  3. 3

    The action

    A configured ticket tool lets the agent submit a request to the service desk.

Knowledge supplies information. Tools perform actions. An agent needs permission to use the data and services involved; an instruction alone does not grant access.

What you are learning: giving an answer and carrying out an action are different capabilities.

This is an illustration, not a claim that our registry record has these capabilities. Module 2 uses an actual agent and checks its result.

Same job / Give it the access the job needs

Opening a ticket does not need access to everything.

Our support agent needs to read the support guide and create a service-desk ticket. A named owner must approve that access.

Needed for this job

  • Read the approved troubleshooting guide.
  • Create a ticket in the service-desk queue.

Not needed for this job

  • Read payroll or HR records.
  • Change employee accounts or grant roles.
This is least privilege: limit access to what the approved task requires. Even approved access does not prove the agent uses it safely.

What you are learning: why agents need an accountable owner and an explicit data/action boundary.

Same job / Management needs evidence

Did it actually open the ticket?

In our teaching example, “I opened a ticket” is a claim, not proof. What evidence would you ask for?

Check the result

Does a real ticket record show the right queue and problem?

Evaluation: was the result right?

Follow recorded steps

Did the recorded ticket-creation call succeed?

Tracing: what steps ran?

Watch over time

Watch failures, response time and usage across requests.

Monitoring: is it reliable over time?

A registry is a list of agents, not proof their tasks worked. Ask the owner for the result and action records.

What you are learning: tell a listed agent, recorded activity and a verified result apart.

Reference: Microsoft Foundry observability (Foundry is Microsoft's platform for building AI apps and agents). The actual runtime and integrations determine what is recorded. No Foundry setup in this module.

Data protection / Microsoft Purview

Protect the data the agent touches.

Our support agent reads a troubleshooting guide and creates tickets. Purview can extend data protection to supported agent activity.

Label it

Sensitivity labels mark confidential information so protection follows it.

Stop unsafe sharing

Data loss prevention (DLP) can warn or block when an agent shares regulated data.

Keep the record

Audit records what the agent accessed and did. It does not block anything.

In Agent 365: Security tab: Microsoft Purview protections

What you are learning: labels, DLP and audit can extend to agents where supported. Audit records; DLP can block.

Security / Microsoft Defender and your security team

Connect the evidence to a decision.

Our support agent's laptop ticket landed in the wrong queue. Where do you start?

  1. 1

    Spot it

    A ticket appears in the wrong queue.

  2. 2

    Find who

    Find the agent and its owner in the registry.

  3. 3

    Investigate

    Defender and your security team compare who signed in with what the agent did.

  4. 4

    Contain

    The authorized team limits the agent's access.

  5. 5

    Check it worked

    No more wrong-queue tickets appear.

  6. 6

    Fix the gap

    Correct the access or guidance, and name an owner.

Two possible causes: its access was misused, or untrusted content (such as hidden text in a document) misled it. A valid sign-in alone cannot tell them apart.
Where would you look? Different questions need different evidence
QuestionWhere to look
Who signed in or changed access?Entra > Entra ID > Monitoring & health > Sign-in logs or Audit logs
Which model or tool steps ran?Ask the runtime owner for recorded traces. Integrated Foundry apps can use Azure Monitor Application Insights.
What workload activity was audited?Purview > Solutions > Audit > Search. Requires supported events, audit access and retention.
Was a threat investigated?Defender > Incidents & alerts > Incidents or Alerts. No alert does not prove no activity.

AI Reader does not grant other evidence roles. Collection and Defender integrations must be verified for the actual runtime; the table is not proof of coverage. The ISOC preview is not required.

What you are learning: a wrong result is a finding, not a diagnosis. Compare evidence before you act.

Business value / Measure results, not activity

Is the support agent worth keeping?

Agent 365 shows an agent is being used, not whether the work was worth it.

Did it solve the problem?

Measure: tickets created correctly the first time.

Did it save effort?

Measure: time per request before and after the agent.

Is the cost worth it?

Measure: licensing, usage and the effort to run and review it.

In Agent 365: Activity tab: shows usage, not value

What you are learning: many chats can still mean many failed requests. Decide what a good result is, then measure it.

Recap / Four questions for any agent

What can you now say about an agent?

See it, control it, protect it. Before you trust any agent, ask four questions.

Management

Is it working?

Check the real result, the recorded steps and reliability. A registry listing is not proof.

Governance

Who owns it, and what can it reach?

An accountable owner approves access limited to the job.

Security

What if it goes wrong?

Spot it, find who, investigate, contain, check it worked, fix the gap.

Business value

Is it worth it?

Measure problems solved, effort saved and cost, not activity.
