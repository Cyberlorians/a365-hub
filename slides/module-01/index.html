Part 2 / Why agents need security

See It.
Control It.
Protect It.

An AI agent is a digital coworker. It reads, makes decisions, and acts with real access.

See it

Know the agent's purpose, owner and operating context.

Control it

Approve its access, data and tool boundaries.

Protect it

Check what happened and act on the evidence.

Companies want agents for the work they do. Our job is to see them, control them and protect them.

Takeaway: explain what the registry shows and one thing it cannot verify. No technical background or written submission needed.

Shared case / Fictional Project Beacon rollout

A weekly status email, not unlimited access.

You are the project coordinator. Give Project Beacon Mail Agent an approved fictional brief: three of four documentation tasks are complete, the architecture diagram still needs review, and the next action is to confirm the review owner.

1. Draft

The agent turns those three facts into a short internal update. No customer data or inbox-reading task is needed.

2. Review

You check the facts, wording and the one instructor-approved internal recipient. Nothing should send before your approval.

3. Send and verify

In Module 2, request the reviewed send and check actual receipt. Today we review the registration only.

Four review questions: What exists? Who owns it and who acts? What can it reach? What evidence shows what happened?

These are intended boundaries, not claims that the registry proves enforcement. In Lab 3, look through the agent's record. No copying exercise or worksheet is needed.

Agent ID scenarios / Orientation, not four deployments

Four scenarios. The same four questions.

Agent 365 customers

Review supported agents through a shared management view.

Microsoft first-party runtimes

Agents run in platforms such as Copilot Studio or Foundry.

Agents anywhere calling Microsoft APIs

An externally hosted agent requests access to Microsoft resources.

Cross-cloud workflows / federation

A workload uses an approved trust to request access across platforms.

These scenarios overlap. Hosting, identity, registry visibility and resource permission are different questions.

Ask the same four questions in every case. Federation alone does not grant resource access. Module 3 traces actual authority.

Same mail task / Two different causes of a wrong action

A valid sign-in does not prove a safe email.

Misused identity or management access

Someone misuses credentials or changes access and sends a Beacon update outside the approved boundary.

Check: sign-ins, changed grants and directory audit records in Entra.

Misleading content

The agent reads an untrusted brief and treats embedded directions as authority. It may send the wrong content or use the wrong recipient while correctly signed in.

Check: the actual request, tool call and result in the deployed agent's runtime logs, plus the sent-message evidence.

The point: an unexpected email is a finding, not a diagnosis. Compare who authenticated with what the agent actually did.

Evidence locations: Entra ID > Monitoring & health > Sign-in logs or Audit logs; Azure portal > the agent's Container App > Monitoring > Log stream. Slide 14 maps the other sources. These are instructor/later-module checks, not extra portals you must access now.

Purview / Data security and compliance follow-through

Protect the data. Record the evidence.

Know your data

Find sensitive information and see who can reach it.

Limit unsafe sharing

Data loss prevention (DLP) can warn or block. Test it on the real workload.

Prove the fix

Compliance Manager tracks each improvement: an owner, an action and a status.

Audit records what happened. It does not block anything.

Module 5 tests one control. A compliance score is not a certification.
